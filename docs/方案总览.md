# AI Native DevKit 方案总览

## 一句话目标

把团队已有的八阶段研发 SOP 变成一个能自动选择轻重流程、管理项目上下文、编排执行、收集验证证据并安全同步文档的 Codex 插件。

## 为什么要做

现有流程的方向是正确的：先读上下文、再澄清和设计，通过测试与文档约束 Agent。但它仍依赖人记住每一步，简单任务也容易进入完整重流程；项目 docs、平台经验和任务状态又缺少统一的加载、更新和晋升机制。

插件要解决四类问题：

1. **流程过重或漏执行**：根据风险选择 Fast、Standard、Strict，而不是所有任务一刀切。
2. **上下文不稳定**：从项目入口和 docs 索引按需加载，保留来源、版本和冲突。
3. **完成缺少证据**：测试、评审和验收都绑定当前 revision 的新鲜证据。
4. **文档容易污染**：任务过程与长期事实分开，验证后才晋升 canonical docs。

## 当前实现边界

### Current 0.4.0

Clarify reuses the Superpowers requirement-understanding behavior without a
runtime dependency, then writes one minimal Git requirements workflow record.
Approval binds its exact path, commit, and blob; Design accepts only that
explicit approved reference. The old checkpoint/result contract is removed
without migrating or deleting external state. The runtime and Skill contract are
0.4.0 implemented; workflow records remain separate from canonical CurrentState.

## Skill 选型结论

### 澄清需求

Current 0.4.0 复用 Superpowers 6.3.0 `Understanding the idea` 的项目检查、范围评估、拆分、一次一个问题和需求理解节奏；DevKit 保留来源引用与精确审批增强，但不建立运行时 Superpowers 依赖。

历史依据仍保留在 `evaluation-evidence.md`：整篇 PRD 评测中两边覆盖均为 32/32、错误假设均为 0，Matt 使用 53 轮，Superpowers 使用 84 轮。2026-08-27 的后续产品决策选择高复用 Superpowers 的需求理解行为；确认内容只进入最小 Git requirements 记录，不写结构化 baseline、长期 domain model 或 ADR。

### 设计方案

采用混合方案：Matt 负责领域决策覆盖和结构化 Spec；Superpowers 提供 2–3 个真实方案、统一维度取舍和高风险章节确认。

依据：设计评测中 Matt 覆盖 13/14 且没有阻塞问题，Superpowers 覆盖 11/14；但 Superpowers 的替代方案和取舍表达更清楚。两边都没有严格通过，因此融合后必须重新评测。

### 实现计划

Current 吸收 Matt `/to-tickets` 的纵向切片机制，但产物是一份从批准 DesignDoc
派生的详细 PlanDoc，不创建 tracker ticket 或依赖图。每个切片都包含设计依据、
公共测试 seam、相关 Red、实现动作、focused verification 和完成条件；迁移、鉴权、
回滚、破坏性动作等细节只在批准设计要求时加入。

依据：两个不同计划案例都显示 Matt 的覆盖接近或等于 Superpowers，但时间和产物规模明显更小，且可执行性更稳定。

### 分阶段执行

不选整套 Matt 或 Superpowers。`$coding-sop` 保持唯一顶层流程；Execute 使用 Matt
风格的行为优先 TDD，按 PlanDoc 顺序串行完成切片，在 final checks 后生成一个
candidate commit，再对固定 baseline-to-candidate diff 做 Spec/Standards 双轴评审。
Current 不维护集中执行台账、tracker frontier 或并发调度。
Plan 启动后出现 design gap 会以 `stage.fail` 结束该 run。Execute 遇到任何既有
worktree/index 变更都为整份 PlanDoc 创建干净隔离工作区；final `Expected` 是 candidate
前以及 candidate 改变后的重复硬门禁。只有 `ExecutionResult.completed` 才由顶层流程继续
Verify、Docs Sync 和 `workflow.finish`，其余状态都以 `stage.fail` 终止当前 run。

依据：05、06 两轮评测各胜一次，说明双方优势在不同层次；直接嵌套两套完整流程会重复编排。

### Debug

E7/E8 仍不足以宣布评测赢家，比较结论维持低到中置信度。2026-08-28 的后续产品决策选择更简单的 Current 组合：插件直接内置 Matt `diagnosing-bugs`，由它负责反馈环、精确/最小复现、排序假设、单变量探针、正确 seam 回归、聚焦修复和清理；`$sop-debug` 只保留 Runtime 生命周期、架构/公共契约停止条件、Verify 和 Docs Hook。

该产品选择不改变历史评测结论，也不预选 Planned V1 的持久 `DiagnosisEngine`。后续实现仍可在 `$sop-debug` 这条 seam 后替换内部调试方法。

### 横切门禁

- TestGate：采用 Matt `tdd` 的公共 seam、可观察行为和纵向 Red→Green。
- ReviewGate：采用 Matt `code-review` 的 Spec 与 Standards 独立审查。
- VerifyGate：采用 Superpowers `verification-before-completion` 的新鲜证据纪律。

这三项是机制借鉴，尚未完成各自独立 A/B。

## 总体架构

```text
用户任务
  → WorkflowRouter
  → ContextCatalog
  → Clarification interview + RequirementDocument
  → DesignEngine
  → $sop-plan / PlanDoc
  → $sop-execute / serial ExecutionResult 或 DiagnosisEngine
  → Execute 内部的 candidate ReviewGate
  → VerifyGate
  → DocsSyncEngine
  → Accepted Done

TaskStateStore 保存仍由它负责的结构化任务状态；Clarify/Design 的需求交接由
Git `RequirementDocRef` 与 Execution Trace 精确审批负责。
```

外部只暴露一个深模块 `WorkflowRuntime`：

```text
run(TaskRequest)    -> TaskOutcome
resume(TaskID)      -> TaskOutcome
status(TaskID)      -> TaskStatus
```

命令 Skill 只是它的 adapter，不拥有第二套生命周期。
0.2 已实现 `$sop-init` 所需的版本化 JSON CLI、plugin-owned `InitEngine`
和剩余通用 TaskStateStore 契约。Current 0.4.0 的 `$sop-clarify` 在访谈完成后
提交一个最小 Git requirements workflow record，由 Execution Trace 精确审批，
再以 `RequirementDocRef` 交给 Design；它不把澄清内容写入 TaskStateStore。
完整 WorkflowRuntime 与 `RouteDecision` 仍属于 Planned V1。

## 任务意图与三档流程

Current `$coding-sop` 已经同时选择 `intent`（`development | debug`）和
`workflowTier`（Fast/Standard/Strict），再投影为兼容的
`route`（`lightweight | development | debug`）。`debug` 是意图，
Fast/Standard/Strict 是流程强度，两者不应混成一个枚举。
Planned V1 新增的是自动风险评分和持久化 `RouteDecision`，不是新的分类词汇。

### Fast

适用于局部、可逆、无产品歧义和公共契约变化的工作：最小上下文 → 实现/诊断 → 定向验证 → docs impact。

### Standard

适用于普通多文件功能和 Bug：上下文 → 必要澄清 → 简洁设计 → PlanDoc → 串行执行及 candidate review → Verify → docs sync。

### Strict

用于架构、数据迁移、鉴权、安全、破坏性动作和难回滚工作：完整决策记录 → 多方案比较与批准 → 带适用 migration/rollback/security 门禁的顺序 PlanDoc → 串行执行 → 全量验证与文档同步。

用户可以升级流程。强制 Strict 信号只能在明确记录风险后人工覆盖。

## docs 的核心设计

始终区分：

```text
CurrentState   = 当前代码、迁移、配置和正式项目文档
RequestedState = Cooper/PRD 与用户确认的目标
ProposedState  = Agent 产生的候选设计
```

0.2 的剩余 Init 与通用任务状态放在目标仓库和插件安装目录之外的 TaskStateStore；
Current Design/Plan prompt Skills 仅在该路径已被仓库规则忽略时，才可以把未提交草稿写入
`.scratch/ai-native-devkit/tasks/<task_id>/`；否则只在当前任务返回内容，不改动仓库或 ignore 规则。
Plan approval 可在 Execution Trace 中携带调用者提供的算法限定 digest；该 identity
不保存 PlanDoc 正文，不把草稿变成 TaskStateStore artifact，也不提供恢复 cursor。
Current Clarify/Design requirement handoff 则使用仓库内的最小 Git 文档和仓库外
Execution Trace 审批；它不是 TaskStateStore artifact。
默认晋升规则：

| 阶段 | 可以写 | 默认不能写 |
|---|---|---|
| 上游同步 | 带 resourceId/版本/hash 的 `references/` 镜像 | 设计和实现状态 |
| `$sop-clarify` | 访谈完成后的一份最小 Git requirements workflow record；审批只在 Trace | 未完成访谈、结构化 baseline、canonical overview/design/API/ADR |
| `$sop-design` | 任务态方案、取舍、ADR candidate、patch 计划 | 当前实现事实 |
| 实现并验证 | 原位更新受影响的 overview/design/API/runbook/status | 日期副本和无关重写 |

确定性索引、链接等可自动更新；领域、架构、接口等语义修改必须先展示 Diff；来源冲突时不写入。

## 首批深模块

| 模块 | 最小接口 | 隐藏的复杂度 |
|---|---|---|
| WorkflowRouter | `route(TaskSignals)` | 风险评分、强制升级、人工覆盖 |
| ContextCatalog | `resolve(ContextRequest)` | docs 路由、版本/hash、冲突和 token 预算 |
| TaskStateStore | `load(task_id)` / `commit(TaskCommit)` | 原子 compare-and-commit、恢复、幂等、schema、脱敏和损坏检测 |
| ExecutionTraceStore | `append` / `load_session` / `load_events` / `load_summary` | Session 映射、追加事件、并发顺序、采集状态和确定性投影 |
| RequirementDocumentWriter | `write_and_commit(...) -> RequirementDocRef` | 安全路径、单文件 Git commit、用户脏状态保护与 blob identity |
| RequirementApprovalGate | `require_approved(...)` | 仓库、精确 subject 和后续用户回合审批投影 |
| RequirementDocumentLoader | `verify_current(...)` / `load_approved(...)` | path/commit/blob、审批、稳定快照和来源 freshness |
| DocsImpactHook | `after_verification` | Git 变更事实、文档影响分类与语义确认信号 |
| Plan Skill adapter（Current） | `plan(approved DesignDoc) -> PlanDoc` | 设计翻译、验收覆盖、顺序纵向切片、按风险补充细节 |
| Execute Skill adapter（Current） | `execute(approved PlanDoc, DesignDoc) -> ExecutionResult` | 单一 baseline、串行 TDD、focused/final checks、candidate commit、有限双轴返工 |
| VerifyGate | `evaluate(AcceptanceSet, EvidenceSet)` | 新鲜度、分母、环境缺口 |
| DocsSyncEngine | `plan(TaskOutcome)` / `apply(ApprovedDocChanges)` | 目标路由、预览、冲突、索引和回执 |

只有真实变化的依赖才定义 adapter，例如 Cooper/内存来源、文件系统/fixture repository、真实工具/脚本 fake、filesystem/in-memory task persistence。

## 开发顺序与状态

1. **0.2 implemented — S0**：Python 标准库实现的版本化 JSON CLI、只读 `$sop-init` Phase 1 运行时、最小版本化契约、TaskStateStore 和冻结 fixture。
2. **Historical 0.2/0.2.3 — S2**：ClarificationCheckpoint / ClarificationResult、baseline 审批和 `task_id` / `ArtifactRef` 澄清恢复契约已由 0.4.0 替代；外部状态保持原样但不再支持。
3. **0.2.3 implemented — Init confirmation gates**：隔离 Init 隐式 caller 的跨仓冲突，并把 Init 选择、读权限和文档写入确认收紧为展示完整内容后结束当前回合、只接受后续用户消息。
4. **0.3 implemented — Execution Trace 与 Docs Hook**：Runtime 激活插件工作流后，插件 Hook 自动采集该工作流的 Host 事件；未使用插件的 Session 不落 Trace。Runtime 同时记录带时间和关联 ID 的阶段/确认事件，对路线必需阶段、确认、验证及 Docs 结果执行完成门禁；Init 与 Docs Sync 自动记录实际路径变化。验证通过后自动进行 Docs 影响分类，不产生 Handoff 建议。插件不再管理 Handoff 接手文档，不扫描、不询问，也不设置专用审批或路径拦截；旧 Trace 仅保留读取兼容。不包含人工评测真值。
5. **0.4.0 implemented — Clarify/Design handoff**：Superpowers-aligned 需求访谈、最小 Git requirements 记录、精确 Trace 审批、跨会话精确引用和来源漂移门禁。
6. **Planned V1 — S1**：ContextCatalog 与 `$sop-init` 的 Bootstrap/Adapt/Refresh 运行时整合。
7. **Planned V1 — S2 完整阶段**：在不引入结构化 clarification baseline 的前提下加强问题排序和冲突门禁。
8. **Planned V1 — S3–S9**：Design、Verify、Debug、DocsSync 的结构化契约与端到端路由，以及尚未预选 engine 接口的 PlanDoc 跨会话选择和 Execute cursor/recovery。

0.2 的 Init Phase 1 薄片不修改目标仓库，也不创建 ContextCatalog 基线；
Current Phase 2 文档流程只在预览和批准后写入，并为下游重建 post-write task/report。
完整的验收步骤和未完成项见 `roadmap-and-validation.md`。

## 关键风险

- Debug 比较评测仍无可靠赢家；Current 使用 Matt 方法是产品简化决策，Planned DiagnosisEngine 仍保持可替换。
- `$sop-execute` 两轮结论相反；融合流程必须复测。
- `$sop-design` 两方都未严格通过；组合不等于自动变好。
- TDD、Review、Verify 尚未独立消融。
- 自动路由可能低估风险，数据库、迁移、鉴权等应有安全下限。
- Cooper 与本地 docs 会漂移，需要来源元数据和冲突处理。
- 直接复制开源 Skill 前必须确认 commit/version/license；优先重写机制而非复制全文。
